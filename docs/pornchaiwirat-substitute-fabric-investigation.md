## 1. วิธีตรวจสอบ

Script: `scripts/scan-pornchaiwirat-substitute-fabric.ts` (read-only)

1. หาออร์เดอร์ทั้งหมดของพรชัยวิรัช (`customerName LIKE '%พรชัยวิรัช%'`) — 178 ใบ
2. หาบิลส่งของ (`fabricouts`/`FabricOut`) ที่ผูกกับออร์เดอร์เหล่านี้ผ่าน `orderId` (หลัก) หรือ `purchaseOrder` (สำรอง เฉพาะแถวที่ไม่มี `orderId`) — 676 แถว
3. เทียบ **สิ่งที่บิลระบุ** (`fabricStruct`/`fabricPattern`/`fabricW`/`customerName`) กับ **ที่มาจริงของสต็อก** (`stockFabricStruct`/`stockFabricPattern`/`stockFabricW`/`stockCustomer`) ทีละแถว แล้ว flag แถวที่:
   - `stockCustomer` ≠ `customerName` (สต็อกมาจากลูกค้าอื่น) หรือ
   - `stockFabricStruct` ≠ `fabricStruct` (โครงสร้างผ้าจริงไม่ตรงกับที่บิล)
4. Group แถวที่ flag เป็นบิล (`vatType`+`vatNo`) แล้วสรุปทีละบิล
5. ทำแบบเดียวกันทั้ง MySQL และ PostgreSQL แล้วเทียบผลว่าตรงกันหรือไม่

รันด้วย: `npx tsx scripts/scan-pornchaiwirat-substitute-fabric.ts`

## 4. หมายเหตุข้างเคียงที่พบระหว่างตรวจ (ไม่ใช่กรณีผ้าทดแทน แต่เกี่ยวข้อง)

การตรวจครั้งแรกจับบิล **A6191** (2026-03-17, ลูกค้า "หจก. มาเจริญซัพพลาย", 47 พับ/5,347 หลา) มาปนด้วย เพราะ `purchaseOrder` เป็นข้อความ **"SO6809/15" ถูกใช้ซ้ำกันใน MySQL โดย 2 ออร์เดอร์คนละใบ**: order id 4150 (มาเจริญ, fabricId `MO1610`) และ order id 4151 (พรชัยวิรัช, fabricId `#527/17 63"`) — ตรวจสอบ `orderId` จริงของบิลนี้แล้วชี้ไปที่ 4150 (มาเจริญ) เสมอ ไม่เกี่ยวกับพรชัยวิรัชเลย จึงตัดออกจากผลลัพธ์ (แก้ script ให้ใช้ `orderId` เป็นหลักและใช้ `purchaseOrder` เป็น fallback เฉพาะแถวที่ไม่มี `orderId` เท่านั้น)

พบเพิ่มเติมว่า **`ast_purchaseorders.purchaseOrder` (เลข SO) ไม่ unique ใน MySQL เก่า — มีค่าเลข PO ซ้ำกันถึง 192 ค่า** ทั้งที่ Prisma schema ฝั่งใหม่กำหนด `@unique` ไว้ ผลคือ **order id 4151 (พรชัยวิรัช, fabricId `#527/17 63"`) ไม่ถูก migrate เข้า PostgreSQL เลย** (ชนกับ id 4150 ที่ครองค่า `purchaseOrder = "SO6809/15"` ไปก่อน) — อย่างไรก็ตาม order 4151 นี้ไม่มีบิลส่งของอ้างอิงถึงมันเลยสักบิล (`fabricouts` ที่มี `orderId=4151` = 0 แถว) จึงไม่กระทบยอดหรือรายงานใดๆ ที่เกี่ยวกับการส่งผ้าจริง — เป็นเพียงออร์เดอร์ที่สร้างไว้เฉยๆ ไม่เคยส่งของ

**ข้อควรทราบ:** ปัญหา PO เลขซ้ำนี้เป็นความเสี่ยงเชิงระบบที่กว้างกว่าเคสนี้ (192 ค่าซ้ำ) — หากต้องการตรวจสอบว่ามีออร์เดอร์ใบอื่นที่ "หายไป" จากการ migrate เพราะชนกับปัญหานี้เหมือน order 4151 อีกหรือไม่ ควรทำการสืบสวนแยกต่างหาก (นอกขอบเขตคำถามนี้)

Script: `scripts/detail-substitute-bills.ts` (read-only) — ดึงทุก field ของทั้ง 2 บิล จากทั้ง MySQL และ PostgreSQL แล้วเทียบทีละพับ (fold) ด้วย `id`

> **หมายเหตุการตรวจ:** รอบแรกที่ลองเทียบโดย `ORDER BY fold` เจอ "mismatch" ปลอมทุกแถว เพราะ `fold` เก็บเป็น VARCHAR ใน MySQL ทำให้ sort แบบ lexicographic ("1","10","11"...) ต่างจาก PostgreSQL ที่ fold เป็น Int (sort เชิงตัวเลข) — แก้โดยเรียงด้วย `id ASC` แทน (id ถูกสร้างเรียงตามลำดับพับจริงตอน insert) ปัญหานี้เป็นแค่ลำดับการแสดงผลของสคริปต์ตรวจสอบเอง ไม่ใช่ความคลาดเคลื่อนของข้อมูลจริง

- ตรวจด้วยการเทียบฟิลด์ `stock*` กับฟิลด์ที่บิลจริง — หากมีการส่งผ้าทดแทนโดยไม่กรอกฟิลด์ `stock*` เลย (เป็น null ทั้งหมด) จะตรวจไม่พบด้วยวิธีนี้ (ตรวจแล้วว่า 592/676 แถวมีฟิลด์ `stock*` กรอกไว้ — ส่วนที่เหลือ ~84 แถวไม่มีข้อมูลนี้ให้เทียบ)
- ไม่ได้ยืนยันกับฝ่ายผลิต/คลังว่าผ้าที่ส่งจริงตรงตามที่ระบบบันทึกหรือไม่ — เป็นการอ่านข้อมูลในระบบเท่านั้น
