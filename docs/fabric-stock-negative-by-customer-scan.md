# ตรวจสอบ: มีลูกค้า/รหัสผ้าอื่นที่ "ส่งออก > รับเข้า" (คงเหลือติดลบ) แบบเดียวกับพรชัยวิรัชหรือไม่

_สืบสวนเท่านั้น 2026-08-20 — อ่านข้อมูลอย่างเดียว 100% ตรวจใน PostgreSQL ตามที่ระบุ ไม่มีการแก้ไขข้อมูลใดๆ_

**สถานะ: ตรวจสอบครบแล้ว**

---

## สรุปสั้น (TL;DR)

- คำนวณ **รับเข้า** (`stockfabrics`) vs **ส่งออก** (`fabricouts`) แยกตาม **(ลูกค้า, โครงสร้างผ้า, หน้ากว้าง)** ทั่วทั้งระบบ — ได้ 513 คู่ลูกค้า×ผ้า
- พบ **255 คู่ (49.7%)** ที่ส่งออก > รับเข้า (คงเหลือติดลบ) — แต่ **แบ่งเป็น 2 ลักษณะที่ต่างกันมาก**:
  - **244 คู่ (95.7%)**: รับเข้า = 0 เป๊ะ (ไม่เคยมีการบันทึกนำเข้าสต็อกเลยสำหรับผ้านั้นของลูกค้านั้น) — **นี่คือปัญหาเชิงระบบที่รู้อยู่แล้ว** โค้ดของหน้า `/api/warehouse/reports/stock-summary` (`route.ts` บรรทัด 59-67) มี comment และ clamp-logic รองรับกรณีนี้อยู่แล้วโดยเฉพาะ (commit `f852a3a` "clamp anomaly rows in stock summary") **ไม่ใช่รูปแบบเดียวกับเคสพรชัยวิรัช** เพราะพรชัยวิรัชมีสต็อกเข้าจริงจำนวนมาก เพียงแต่ยืมข้ามลูกค้าเป็นบางบิล
  - **11 คู่ (4.3%)**: **มีรับเข้าจริง > 0 แต่ส่งออกเกินไป** — กลุ่มนี้ใกล้เคียงกับรูปแบบพรชัยวิรัชมากกว่า (มีฐานสต็อกอยู่บ้าง แต่ไม่พอ)
- **พรชัยวิรัชเองไม่ติดอยู่ในรายการติดลบเลย** เมื่อคิดยอดรวมทั้งลูกค้า — รหัสผ้า `#527/17 60"` มี รับเข้า=71,098 หลา ส่งออก=68,167 หลา คงเหลือ **+2,931 หลา (บวก)** เพราะยอดที่ยืมมาจาก "มนตรา เทรดดิ้ง"/"ACCESS" เป็นแค่ 2 บิลกลางไทม์ไลน์ ไม่ได้ทำให้ยอดสะสมทั้งหมดติดลบ

## 1. วิธีคำนวณ

Script: `scripts/scan-fabric-stock-negative-by-customer.ts` (read-only)

```
รับเข้า (customer, fabric) = SUM(sumYard) จาก stockfabrics WHERE deleted_at IS NULL
                              GROUP BY customer, fabricStruct(normalize), fabricW(normalize)
ส่งออก (customer, fabric)  = SUM(sumYard) จาก fabricouts WHERE deleted_at IS NULL
                              GROUP BY customerName, fabricStruct(normalize), fabricW(normalize)
คงเหลือ = รับเข้า - ส่งออก
```

**Normalize ที่ใช้** (สำคัญมาก — พบระหว่างตรวจว่าถ้าไม่ normalize ให้ถูกต้อง จะเกิด false-positive จำนวนมาก):
- `fabricW`: ตัดเอาเฉพาะตัวเลขนำหน้า (เดียวกับสูตรที่ใช้ในหน้า stock-summary จริงของแอป เช่น "50/V1-V1" → "50")
- `fabricStruct`: **ลบช่องว่างทั้งหมดออก** (ไม่ใช่แค่ยุบเหลือช่องเดียว) เพราะพบว่า `stockfabrics` บันทึกแบบ `"KE 20 * KE 20 / 104 * 50"` (มีช่องว่างระหว่างตัวอักษรกับตัวเลข) แต่ `fabricouts` บันทึกแบบ `"KE20  * KE20  / 104 * 50"` (ไม่มีช่องว่าง) — ถ้าใช้ regex เดียวกับหน้ารายงานจริงของแอป (ที่ไม่ normalize fabricStruct เลย) ผ้าชนิดเดียวกันจะถูกนับเป็นคนละกลุ่ม ทำให้ตัวเลขรับเข้า/ส่งออกเพี้ยน (พบกับกรณีพรชัยวิรัชเองเป็นตัวอย่างแรก — ก่อนแก้ normalize สคริปต์รายงานผิดว่าพรชัยวิรัชรับเข้า=0)

## 5. ข้อจำกัดและคำเตือน

- **กลุ่ม "รับเข้า=0" (244 รายการ) ไม่เทียบเท่ากับการยืนยันว่ามีการทดแทนผ้าจริง** — อาจหมายถึงกระบวนการทำงานที่ผ้าถูกส่งตรงจากการผลิตโดยไม่เคยผ่านขั้นตอนบันทึก "รับเข้าสต็อก" เลย (workflow ปกติสำหรับบางลูกค้า) หรือความคลาดเคลื่อนของการสะกดชื่อลูกค้า/โครงสร้างผ้าที่ normalize ไม่ครอบคลุมหมด — **ต้องตรวจแบบเจาะราย-บิล (เหมือนที่ทำกับพรชัยวิรัชในข้อ 1) ก่อนสรุปว่าเป็นปัญหาจริง**
- คำนวณจาก PostgreSQL เท่านั้นตามที่ระบุในคำถาม ไม่ได้เทียบกับ MySQL เก่า
- Normalize fabricStruct ด้วยการลบช่องว่างทั้งหมด+ตัวพิมพ์ใหญ่ อาจทำให้ผ้าคนละชนิดที่บังเอิญมีตัวอักษร/ตัวเลขเรียงเหมือนกันถูกนับรวมกัน (ความเสี่ยงต่ำ เพราะ fabricStruct มีรูปแบบเฉพาะเจาะจงสูง)
- ตัวเลข 11 รายการในข้อ 3 ยังไม่ได้ตรวจแบบเจาะราย-บิลว่าเป็น "ยืมสต็อกข้ามลูกค้าแบบเดียวกับพรชัยวิรัช" จริงหรือไม่ (ต้องดู field `stockCustomer`/`stockFabricStruct` ของแต่ละบิลเหมือนที่ทำกับพรชัยวิรัช) — เป็นเพียง candidate list ระดับสรุปยอดเท่านั้น
