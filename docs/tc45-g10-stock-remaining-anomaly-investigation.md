- **ไม่ใช่บั๊ก fan-out** ที่เคยแก้ไปแล้ว — สูตรใน `src/lib/materialStock.ts` ยัง pre-aggregate ทุก source table เป็น 1 แถวต่อ `materialId` ก่อน JOIN ถูกต้องดี
- **ไม่ใช่ข้อมูล averageKg ผิดปกติซ่อนอยู่แบบ id=460/3984** — สแกนทั้ง 234 แถวของ yarnType นี้แล้ว ไม่มีแถวไหน `weightKgSum/spool` ผิดปกติ (>4kg/spool) เลยสักแถวเดียว
- 3 รายการที่เพิ่งแก้ไป (id=1161, 1308, 1480) **ไม่ได้ถูกเปลี่ยนชื่อเป็น "(เหลือสืบ)"** อย่างที่สันนิษฐาน — ยังคงเป็น `yarnType='TC 45 COMB (65:35) G 10'` เหมือนเดิม (คนละ id กับ 2 แถวที่มี suffix "(เหลือสืบ)" จริงคือ id=2226, 2275) จึงไม่มีปัญหานับซ้ำ/แยกกลุ่มผิด — 3 แถวนี้ไม่ใช่สาเหตุของความผิดปกติ (averageKg ต่ำ 0.08–0.58 kg/spool อยู่แล้ว)
- **สาเหตุจริง: บั๊กใน `scripts/sync-from-mysql.ts` ตอน match `materialrequisitions`/`material_outsides` เข้ากับ `materials`** — ใช้ `Map` คีย์ `lot|yarnType|supplierName` (บรรทัด 436-440) ซึ่ง **ไม่ unique** เพราะเลข lot เช่น "1", "2", "3" ถูกใช้ซ้ำกับ batch นำเข้าจริงหลายสิบ/หลายร้อยครั้งจากซัพพลายเออร์เดียวกัน `Map.set()` ทับกันเรื่อยๆ เหลือ materialId ผู้ชนะเพียงตัวเดียวต่อ lot → ธุรกรรมเบิกทั้งหมดของทุก batch ที่ควรกระจายไปหลายแถว กลับถูกยัดไปที่แถวเดียว ทำให้แถวนั้น remaining ติดลบมหาศาล ในขณะที่แถวอื่นๆ ที่แชร์ lot เดียวกันดูเหมือนไม่เคยถูกเบิกเลย (remaining = total เต็ม) ผลรวมสุดท้าย remainingSpool ที่ระดับกลุ่มยังถูกต้อง (เพราะบวกลบหักกลบกันพอดี) แต่ **อัตราส่วน kg/spool ของยอดคงเหลือบิดเบือนรุนแรง** เพราะเป็นผลหารของผลต่างของตัวเลขใหญ่สองตัวที่เกือบเท่ากัน (catastrophic cancellation) — ไม่ใช่บั๊กในสูตร SQL ของหน้าสต็อกเอง

## 1. ยืนยันสูตรคำนวณ — ไม่ใช่ fan-out บั๊กที่เคยแก้

`src/lib/materialStock.ts` (`MATERIAL_STOCK_CTES`) มี CTE `req`, `out_w`, `ret` ที่ `GROUP BY "materialId"` ก่อนเสมอ (1 แถวต่อ 1 materialId) แล้วค่อย `LEFT JOIN` เข้ากับ `materials` — ป้องกัน fan-out ตอน `SUM()` ที่ระดับ group-by-yarnType รอบนอกแล้ว มี comment กำกับไว้ชัดเจนในโค้ดว่าเป็นการแก้ปัญหานี้โดยเฉพาะ (บรรทัด 15-17)

สูตร `remaining = total - (req + req_orphan + out_w) + ret` ถูกต้องตามตรรกะ ยืนยันด้วยการรัน query เดียวกันแบบ manual (ไม่ผ่าน CTE ที่ share) ได้ผลตรงกับ endpoint จริงทุกตัวเลข

## 2. Query materials ทั้งหมดของ "TC 45 COMB (65:35) G 10" (234 แถว) — หา remaining ผิดปกติ

Group-by ผ่านสูตรจริงของหน้าสต็อก (ข้อมูล ณ ตอนสืบสวน ใกล้เคียงตัวเลขที่รายงานมา ต่างกันเล็กน้อยจากข้อมูลใหม่ที่เข้ามาระหว่างนั้น — usedSpool/usedWeightKg ตรงกันเป๊ะ ยืนยันว่าเป็นกลุ่มเดียวกัน):

|---|---|---|---|

| 3517 | 1 | บริษัท แพรกษาเท็กซ์ไทล์ จำกัด | 180 | **-15,159** | **-29,350.61** |

สาเหตุของ 3 แถวนี้: มีธุรกรรม `materialrequisitions`/`material_outsides` ที่ผูก `materialId` ตรงมาที่ id เหล่านี้ **มากเกินจริงหลายสิบ/หลายร้อยเท่า** ของ spool ที่แถวนั้นเคยมี เช่น id=3517 มี totalSpool แค่ 180 แต่มีแถว `materialrequisitions` ที่ `materialId=3517` ถึง **225 แถว รวม 14,869 spool** (82 เท่าของยอดรับจริง), id=4272 มี totalSpool 1,895 แต่มี requisition **781 แถว รวม 292,553 spool** (154 เท่า)

**สาเหตุตรงจุด — บั๊ก join-key collision ใน sync script:**
`scripts/sync-from-mysql.ts:436-440` สร้าง lookup map สำหรับ match `materialrequisitions`/`material_outsides` เข้ากับ `materials` ด้วยคีย์ `lot|yarnType|supplierName`:
```ts
const matLookup = new Map<string, number>()
for (const m of materials) {
  const key = `${m.lot ?? ''}|${m.yarnType ?? ''}|${m.supplierName ?? ''}`
  matLookup.set(key, Number(m.id))   // ← ทับกันเรื่อยๆ ถ้า key ซ้ำ
}
```
ปัญหาคือเลข `lot` เช่น "1", "2", "3" **ไม่ใช่ค่า unique ต่อ batch นำเข้าจริง** — ยืนยันด้วยการนับ:

| lot | จำนวนแถว materials ที่ยี่ห้อ/ซัพพลายเออร์เดียวกันแชร์ lot นี้ | จำนวนแถวที่มีธุรกรรมเบิกมาผูกด้วยจริง |
|---|---|---|
| "1" | 16 | **1** (id=3517 ได้ไปทั้งหมด) |
| "2" | 34 | **1** (id=1858 ได้ไปทั้งหมด) |
| "3" | 181 | **1** (id=4272 ได้ไปทั้งหมด) |

จาก 231 แถว materials ของซัพพลายเออร์ "บริษัท แพรกษาเท็กซ์ไทล์ จำกัด" ในกลุ่มนี้ **มีแค่ 3 แถวที่ถูก sync ผูกธุรกรรมเบิกเข้ามาเลย ที่เหลือ 228 แถว remaining = total เต็ม (ไม่เคยถูกเบิกตามข้อมูลในระบบ)** เพราะตอน sync `Map.set()` ทับกันเหลือผู้ชนะ 1 คนต่อ lot แล้วธุรกรรมทั้งหมดของ batch อื่นๆ ที่แชร์ lot เดียวกันไปกองรวมที่ผู้ชนะคนเดียว

**ผลลัพธ์ที่ระดับกลุ่ม:** remainingSpool รวม (28,756) ถูกต้องในเชิงตัวเลข (ผลบวกลบของแถวปกติ 228 แถว vs 3 แถวติดลบมหาศาลหักกลบพอดี) แต่ **อัตราส่วน kg/spool ของผลต่างนั้นบิดเบือนรุนแรง** เพราะ:
- แถวปกติ 228 แถว: remaining ≈ total, ratio ≈ 2.34 kg/spool (ใกล้เคียงค่าเฉลี่ยรวม)
- แถวติดลบ 3 แถว: ratio ≈ 1.92 kg/spool (ใกล้เคียงค่าเฉลี่ยใช้ไปแล้ว)
- ผลต่างของตัวเลขใหญ่สองก้อนที่ใกล้เคียงกัน (367,565 หัก 338,809 = 28,756) ทำให้ ratio ของผลต่าง (7.30) เพี้ยนไปจาก ratio ของทั้งสองก้อนต้นทาง — เป็น artifact ทางคณิตศาสตร์ (catastrophic cancellation) ไม่ใช่ปรากฏการณ์ทางกายภาพจริง

ซัพพลายเออร์ที่โดนหนักสุดคือ **บริษัท จงสถิตย์ จำกัด** (yarnType "KE 20" เจอ 7 กลุ่ม lot ที่โดน, รวมกับ yarnType อื่นๆ ของซัพพลายเออร์เดียวกันอีกหลายรายการ) และ **บริษัท แพรกษาเท็กซ์ไทล์ จำกัด** (พบใน TC 45 COMB (65:35) G 10 ที่กำลังสืบสวนอยู่ รวมถึง CD 20 CARD, TC 45 COMPACK, CD 32 CARD ฯลฯ อีกหลายรายการ) — **รูปแบบเดียวกับที่พบใน TC 45 COMB (65:35) G 10 ทุกประการ**: เลข lot ("1","2","3","P(50)","00E201-29" ฯลฯ) ถูกใช้ซ้ำข้าม batch นำเข้าจริงหลายสิบ-หลายร้อยครั้งของซัพพลายเออร์เดียวกัน ทำให้ `Map` ใน sync script ทับกันเหลือผู้ชนะทีละแถว

**สรุป:** บั๊ก join-key collision นี้ไม่ใช่กรณีพิเศษของ TC 45 COMB (65:35) G 10 แต่เป็น **ข้อบกพร่องเชิงโครงสร้างของ `scripts/sync-from-mysql.ts`** ที่กระทบข้อมูล remaining ของ materials ส่วนใหญ่ในระบบ (81% ของแถวทั้งหมดอยู่ในกลุ่มเสี่ยง) การแก้ต้องพิจารณาระดับ sync/matching logic ทั้งหมด ไม่ใช่แก้ทีละ yarnType — **ยังไม่ได้ตัดสินใจแนวทางแก้ไขใดๆ**

## 7. ⚠️ ข้อแก้ไขสำคัญก่อนประเมินทางแก้ (2026-08-06 ต่อเนื่อง)

ก่อนประเมินทางแก้ พบข้อเท็จจริงสำคัญที่ต้อง **แก้ไขความเข้าใจจากหัวข้อ 1-6** ด้านบน:

**ยืนยันด้วยการเทียบ ground-truth แล้วว่า: ยอดรวมระดับ yarnType+supplierName (Σ used, Σ remaining) ไม่ได้รับผลกระทบจากบั๊ก collision เลย** — เทียบ Σ usedSpool/usedWeightKg ที่คำนวณผ่านสูตร join ปกติ (ที่ผ่าน materialId ซึ่งมี collision) กับค่าที่ query ตรงจาก `materialrequisitions`/`material_outsides` โดยใช้ field `yarnType`/`supplierName` ที่ denormalize ไว้บนแถวธุรกรรมเอง (ข้าม materialId ไปเลย) — **ผลตรงกันเป๊ะทุกตัวเลข (DIFF=0)** ทดสอบแล้ว 3 คู่ (TC 45 COMB (65:35) G 10 + แพรกษาเท็กซ์ไทล์, KE 20 + จงสถิตย์, C 20 OE + กังวาลเท็กซ์ไทล์)

**เหตุผลเชิงคณิตศาสตร์:** `matLookup` ผูก materialId เฉพาะแถวที่ yarnType+supplierName **ตรงกับตัวเอง** เท่านั้น (ผูกผิดแค่ "lot ไหนในกลุ่มเดียวกัน" ไม่เคยผูกข้าม yarnType/supplier) ดังนั้นเมื่อ SUM รวมทุก materialId ในกลุ่ม yarnType+supplierName เดียวกัน ผลรวมจะถูกต้องเป๊ะเสมอ ไม่ว่าตัวชนะภายในจะเป็นแถวไหน — **บั๊กนี้กระทบแค่ระดับ "รายแถว/รายล็อต" (per-materialId) เท่านั้น ไม่กระทบระดับ yarnType หรือ yarnType+supplierName**

**ผลตามมา: ค่าเฉลี่ย "คงเหลือ" 7.78 kg/spool ที่ดูผิดปกติ (หัวข้อ 2) ไม่ได้เกิดจากบั๊ก collision** — เป็นผลลัพธ์ทางคณิตศาสตร์ที่ถูกต้องของ Σtotal และ Σused จริง (ซึ่งทั้งคู่ถูกต้อง 100%) แค่บังเอิญว่า usedAvg (1.93) ต่ำกว่า totalAvg (2.35) อยู่พอสมควร (~18%) และเหลือของจริงอยู่แค่ ~7.8% ของยอดทั้งหมด — ผลต่างเล็กๆ ของตัวเลขใหญ่สองก้อนที่ใกล้เคียงกันทำให้ ratio ของส่วนที่เหลือแกว่งแรง (catastrophic cancellation) **นี่คือปรากฏการณ์ทางคณิตศาสตร์ปกติ ไม่ใช่บั๊ก** — จะเกิดขึ้นเหมือนเดิมแม้ไม่มี matLookup collision บั๊กเลยก็ตาม

**ตรวจ UI/API ทั้งหมดที่ใช้ `remainingSpool`/`remainingWeightKg` แล้ว (`grep -rn` ทั้ง `src/`) พบว่า:**
- `/api/warehouse/material/stock` (ทั้ง grouped-by-yarnType และ flat-by-company) — group ที่ระดับ **yarnType** และ **yarnType+supplierName** เท่านั้น ไม่มี breakdown ราย lot เลย
- `/api/warehouse/material/average-weight` — match ด้วย **yarnType+supplierName** เท่านั้น (exact match ไม่ใช่ lot)
- `MaterialStockCompanyRow` type (`src/types/material.ts`) **ไม่มี field `lot` เลย**

**สรุปข้อแก้ไข: ไม่มีหน้าจอ/API ไหนในระบบปัจจุบันที่โชว์หรือใช้ remaining ระดับราย lot (per-materialId) เลยสักจุดเดียว** ทุกจุดที่ผู้ใช้เห็นวันนี้ (หน้าสต็อก, auto-fill น้ำหนักเฉลี่ยตอนเบิก) **คำนวณถูกต้องอยู่แล้ว แม้จะมีบั๊ก collision ซ่อนอยู่ก็ตาม** — บั๊กนี้เป็น **latent data-integrity issue ที่ซ่อนอยู่ในค่า `materialId` ของธุรกรรมเก่าที่ sync เข้ามา** เท่านั้น จะโผล่มาเป็นปัญหาจริงก็ต่อเมื่อมีใครสร้างฟีเจอร์ใหม่ที่ต้องพึ่งพา materialId ระดับ lot (เช่น export/report เจาะจงล็อต แบบที่ใช้สืบสวนเรื่องนี้เอง, ระบบ traceability, FEFO/lot-specific alert ในอนาคต) — **ไม่ใช่บั๊กเร่งด่วนที่กระทบผู้ใช้งานตอนนี้**

## 8. สำรวจ MySQL ต้นทาง — มี field เชื่อมโยงแม่นยำกว่านี้ไหม?

`DESCRIBE materialstores` และ `DESCRIBE material_outsides` บน MySQL ต้นทาง (ผ่าน SSH tunnel เดิม) — ตรวจทุก column แล้ว:

**materialstores:** `id, withdrawId, department, emp, supplierName, yarnType, lot, spool, weight_p_net, weight_kg_net, average_p, average_kg, createDate, created_at, updated_at`

**material_outsides:** `id, emp, supplierName, createDate, yarnType, lot, pallet, box, sack, spool, weight_p_sum, weight_kg_sum, weight_p_package, weight_kg_package, weight_p_net, weight_kg_net, average_p, average_kg, recipient, comment, created_at, updated_at, paymentComment`

**ไม่มี column ไหนเป็น FK ตรงไปยัง `materials.id` เลยแม้แต่ column เดียว** — ระบบ Laravel เดิมไม่เคยเก็บว่าการเบิกแต่ละครั้งมาจาก batch (แถว materials) ไหนโดยเฉพาะ เก็บแค่ `yarnType + supplierName + lot` (เป็น string ธรรมดา ไม่ unique) เท่านั้น **นี่คือข้อจำกัดของข้อมูลต้นทางจริง ไม่ใช่ความผิดพลาดตอน migrate/sync เข้า ast-new** — `lot|yarnType|supplierName` เป็นกุญแจที่ดีที่สุดเท่าที่มีอยู่แล้วจากต้นทาง

## 9. ทดลอง FIFO matching ด้วยเวลา (ยัง MySQL ต้นทางเท่านั้น ไม่แตะ Postgres)

จำลอง FIFO: เรียง materials (batch รับเข้า) ตาม `createDate` จากเก่าไปใหม่ เรียงธุรกรรมเบิก (`materialstores` + `material_outsides`) ตาม `createDate` เดียวกัน แล้วจับคู่แบบ "เบิกจาก batch เก่าสุดที่ยังมีของเหลือก่อน" ไล่ทดสอบ 7 กลุ่มที่ collision รุนแรงสุด:

| yarnType | supplier | lot | จำนวน batch | shortfall (เบิกเกินยอดรับสะสม) | batch ติดลบหลัง FIFO |
|---|---|---|---|---|---|
| TC 45 COMB (65:35) G 10 | แพรกษาเท็กซ์ไทล์ | 3 | 181 | 0 | 0 |
| TC 45 COMB (65:35) G 10 | แพรกษาเท็กซ์ไทล์ | 2 | 34 | 0 | 0 |
| TC 45 COMB (65:35) G 10 | แพรกษาเท็กซ์ไทล์ | 1 | 16 | 0 | 0 |
| C 20 OE | กังวาลเท็กซ์ไทล์ | P(50) | 146 | 0 | 0 |
| KE 20 | จงสถิตย์ | 00E201-29 | 667 | 0 | 0 |
| **KE 20** | **จงสถิตย์** | **00E201-19** | **347** | **5,290 spool (22 ธุรกรรม)** | **0** |
| TC 45 COMB | กังวาลเท็กซ์ไทล์ | 11 | 49 | 0 | 0 |

**ผล: 6 ใน 7 กลุ่ม FIFO ให้ผลลัพธ์สมบูรณ์แบบ** — ไม่มี batch ไหนติดลบเลย, ไม่มี shortfall, การกระจาย usage สมเหตุสมผล (เช่น TC45 lot=3: 173/181 batch มี usage, เหลือ 8 batch ล่าสุดที่ยังไม่ถูกเบิกเลย — ตรงกับสามัญสำนึกว่า stock ที่เพิ่งรับเข้าล่าสุดควรยังไม่ถูกแตะ)

**1 ใน 7 กลุ่มมี shortfall จริง** (KE 20 lot=00E201-19): withdrawal รวม (103,733 spool) **เกิน** ยอดรับรวม (98,443 spool) แม้จัดเรียงตามเวลาแบบ FIFO แล้วก็ตาม — แปลว่านี่ไม่ใช่ปัญหาการจับคู่ (matching) แต่เป็น**ข้อมูลจริงที่ไม่ครบ** (อาจมี batch รับเข้าบางรายการไม่เคยถูกบันทึกใน `materials`, หรือมีธุรกรรมเบิกบางรายการติด lot ผิดตั้งแต่ตอนกรอกในระบบ Laravel เดิม) — เป็นข้อจำกัดที่จะเหลืออยู่ไม่ว่าเลือกวิธีไหน แต่ **ขนาดเล็กกว่าเดิมมาก** (shortfall 5,290 จาก 98,443 = 5.4% เทียบกับ collision เดิมที่ทำให้ 1 แถวติดลบถึง 292,498 spool)

## 10. ผลกระทบของแนวทาง "ยกเลิก tracking ระดับ lot เปลี่ยนไปที่ yarnType+supplier"

จากข้อ 7 ที่พิสูจน์แล้วว่า **ไม่มีจุดไหนในระบบปัจจุบันใช้ remaining ระดับ lot เลย** แนวทางนี้แปลว่า:

- **หน้าสต็อกวัตถุดิบ (grouped + flat-by-company):** **ไม่กระทบเลย** — คำนวณที่ระดับ yarnType/yarnType+supplierName อยู่แล้วตั้งแต่ต้น ไม่ต้องแก้อะไร
- **Auto-fill น้ำหนักเฉลี่ยตอนเบิก (`/api/warehouse/material/average-weight`):** **ไม่กระทบเลย** — match ด้วย yarnType+supplierName exact อยู่แล้ว ไม่เคยอิง lot
- **สิ่งที่ต้องแก้จริงถ้าเลือกแนวทางนี้:** แก้ที่ `scripts/sync-from-mysql.ts` (และ `sync-from-mysql-upsert.ts`) ให้เลิกพยายาม resolve `materialId` แบบเจาะจงราย lot สำหรับ `materialrequisitions`/`material_outsides` ที่ sync เข้ามา (ปล่อยเป็น `null` แล้วให้ `req_orphan` CTE ที่มีอยู่แล้วรับช่วงกระจายเฉลี่ยแทนทั้งหมด — เป็นกลไกเดียวกับที่ใช้กับแถวที่ lookup พลาดอยู่แล้วในปัจจุบัน) เท่ากับขยายกลไกที่มีอยู่ให้ครอบคลุมทุกกรณี ไม่ใช่สร้างของใหม่
- **ข้อเสีย:** ทิ้งความแม่นยำระดับ lot ของ ~19% ของแถว materials (822 จาก 4,369 แถว) ที่ **ไม่ได้ติด collision** ไปด้วย (คือกรณีที่ lot label unique จริงในกลุ่ม yarnType+supplier นั้นๆ อยู่แล้ว การ map ปัจจุบันถูกต้องอยู่แล้วสำหรับแถวเหล่านี้) — ถ้าในอนาคตมีคนอยากทำฟีเจอร์ระดับ lot (traceability, FEFO, lot-specific alert) จะไม่มีข้อมูลให้ใช้เลย ต้องเริ่มใหม่หมด

## 11. เปรียบเทียบ 2 แนวทาง

| หัวข้อ | (1) FIFO matching (backfill + แก้ sync) | (2) ยกเลิก lot-level ไปที่ yarnType+supplier |
|---|---|---|
| **ความจำเป็นเร่งด่วน** | ต่ำ — ไม่มีอะไรพังในหน้าจอปัจจุบัน (ยืนยันแล้วข้อ 7) | เดียวกัน |
| **ความแม่นยำที่ได้** | สูง — ทดสอบ 6/7 กลุ่มไม่มี batch ติดลบเลย, ยังคงความละเอียดระดับ lot ไว้ (มีประโยชน์ถ้าต้องการ traceability ในอนาคต) | ยอมรับว่าไม่มีความละเอียดระดับ lot อีกต่อไป (แม้ 19% ของข้อมูลจะแม่นอยู่แล้วก็ทิ้งไปด้วย) |
| **ความซับซ้อนการ implement** | **สูงกว่า** — ปัญหาหลักคือ schema ปัจจุบัน `materialrequisitions.materialId`/`material_outsides.materialId` เป็น FK เดี่ยว (1 ธุรกรรม → 1 lot เท่านั้น) แต่ FIFO บางครั้งธุรกรรมเดียวต้องตัดคาบเกี่ยว 2 batch (เช่น เบิก 3,000 ลูก แต่ batch ปัจจุบันเหลือ 1,220 ลูก ต้องดึงจาก batch ถัดไปอีก 1,780) ต้องเลือก: (ก) ปัดเป็น batch เดียวที่ดึงเยอะสุด (ประมาณ ไม่เป๊ะ 100% ตรงจุดรอยต่อ) หรือ (ข) เพิ่มตาราง allocation ใหม่ (transactionId, materialId, spool, weight) รองรับ many-to-many จริง (schema migration + เขียน aggregation ใหม่ทั้งหมด) | **ต่ำ** — แก้ 2 sync script ให้ปล่อย materialId เป็น null แล้วให้กลไก req_orphan เดิมรับช่วง (ของที่มีอยู่แล้ว ไม่ต้องสร้างใหม่) |
| **ต้องรันย้อนหลังกับข้อมูลเก่าไหม** | ต้อง — ต้อง re-backfill materialId ของธุรกรรมเก่าทั้งหมดที่เคย sync ผิดมาแล้ว (136 กลุ่ม, 3,547 แถว) | ต้อง — ต้อง set materialId = null ให้ธุรกรรมที่เคย mis-attribute ไปแล้ว (เพื่อไม่ให้ยังโชว์ remaining ติดลบราย lot ถ้ามีใคร query ตรงในอนาคต) |
| **ป้องกันบั๊กเกิดซ้ำตอน sync ครั้งถัดไปไหม** | ต้องแก้ sync script ให้ทำ FIFO ตอน insert ใหม่ด้วย (ไม่ใช่แค่ backfill ครั้งเดียว) เพราะ `update.sh` เรียก sync ซ้ำได้เรื่อยๆ | ป้องกันได้ทันทีและถาวร (เพราะเลิกพยายาม attribute ราย lot ไปเลย ไม่มีทางชนกันอีก) |
| **Known residual limitation** | บาง lot อาจยังมี shortfall จริงจากข้อมูลต้นทางไม่ครบ (พบ 1/7 กลุ่มทดสอบ, ~5% ของ volume กลุ่มนั้น) — เล็กกว่าเดิมมากแต่ไม่หายสนิท 100% | ไม่มี residual — ยอดรวมถูกต้องแน่นอนเสมอ (พิสูจน์แล้วข้อ 7) |
| **คุ้มค่าหรือไม่ ถ้าไม่มีแผนทำฟีเจอร์ระดับ lot** | ROI ต่ำ — ลงทุนสูง (โดยเฉพาะถ้าอยากได้ split allocation ที่แม่นจริง) เพื่อแก้สิ่งที่ไม่กระทบผู้ใช้งานตอนนี้ | ROI สูงกว่า — งานน้อย ตรงไปตรงมา แก้ latent bug ให้จบโดยไม่ต้องเสี่ยง regression |

**ข้อเสนอเบื้องต้น (ยังไม่ implement):** เนื่องจากยืนยันแล้วว่า **ไม่มีฟีเจอร์ปัจจุบันไหนพังจากบั๊กนี้** คำถามสำคัญที่ต้องตอบก่อนเลือกทางคือ "มีแผนจะทำฟีเจอร์ระดับ lot (traceability/FEFO/lot alert) ในอนาคตอันใกล้ไหม" — ถ้าไม่มีแผน แนวทาง (2) ให้ผลตอบแทนคุ้มกว่ามากในทันที (งานน้อย, ป้องกันซ้ำถาวร, ไม่มี residual) ถ้ามีแผนจริง แนวทาง (1) คุ้มค่าลงทุนระยะยาวกว่า แต่ต้องตัดสินใจเรื่อง split-allocation schema ก่อนเริ่ม — **รอ decision จากผู้ใช้**

คำถามต่อยอด: ข้อ 7 พิสูจน์แล้วว่าผลรวม (Σtotal, Σused, Σremaining) ที่ระดับ yarnType/yarnType+supplierName ถูกต้อง 100% เสมอ ไม่ได้รับผลกระทบจากบั๊ก collision — แต่ ratio `avgRemaining/avgTotal` ที่ดูผิดปกติของ TC 45 COMB G 10 (7.30 vs 2.35 = 3.1x) เป็น **catastrophic cancellation ปกติทางคณิตศาสตร์** (ข้อ 7) ไม่ใช่บั๊ก คำถามคือ: ปรากฏการณ์นี้เกิดกว้างแค่ไหนในระบบจริง?

สคริปต์ `scripts/scan-stock-remaining-anomaly.ts` (read-only, ใช้สูตรเดียวกับหน้าสต็อกจริงจาก `src/lib/materialStock.ts`) สแกนครบทั้ง **177 yarnType** ในระบบ คำนวณ `avgTotal = totalWeightKg/totalSpool`, `avgUsed`, `avgRemaining` แล้ว flag:

**สรุปข้อ 12:** ปรากฏการณ์ "ค่าเฉลี่ยคงเหลือสูงผิดปกติ" ไม่ใช่บั๊กเดี่ยวของ TC 45 COMB G 10 แต่เป็น **ผลข้างเคียงทางคณิตศาสตร์ที่คาดได้** ของสต็อกที่เหลือน้อย (ใกล้หมด) — เกิดกับ 15.3% ของ yarnType ในระบบ ไม่ต้องแก้โค้ด/สูตร เพราะตัวเลขที่แสดงถูกต้องอยู่แล้ว (ยืนยันซ้ำจากข้อ 7) แต่ **อาจพิจารณาเพิ่ม UI hint** (เช่น ไม่โชว์ ratio หรือ avg เมื่อ remainingSpool ต่ำกว่า threshold หนึ่ง) เพื่อไม่ให้ผู้ใช้เข้าใจผิดว่าเป็นบั๊ก — ยังไม่ตัดสินใจ ส่วน **8 yarnType ที่ remaining ติดลบจริงที่ระดับกลุ่ม** เป็นคนละประเด็น (ข้อมูลต้นทางไม่ครบ ไม่ใช่ catastrophic cancellation) สมควรตรวจสอบแยกต่างหากถ้าต้องการแก้

## 13. ตรวจสาเหตุ 8 yarnType ที่ remaining ติดลบที่ระดับกลุ่ม (2026-08-06 ต่อเนื่อง)

สืบสาเหตุ (read-only) ของแต่ละ 8 กลุ่ม โดยแยกส่วนประกอบ (req / out_w / req_orphan) และเช็ค 2 สมมติฐานที่เป็นไปได้:

1. **materialId ผูกข้ามกลุ่มผิด** (ธุรกรรมที่ denormalize `yarnType`/`supplierName` ไว้บนแถวตัวเองไม่ตรงกับกลุ่มที่ materialId พาไป) → เช็คทุกแถว req/out_w/ret ของทั้ง 8 กลุ่ม **พบ mismatch = 0 แถวทุกกลุ่ม** — materialId ที่ผูกไว้ยังอยู่ในกลุ่ม yarnType+supplierName เดียวกันเสมอ ไม่มีการรั่วข้ามกลุ่ม
2. **ธุรกรรมซ้ำจากข้อมูลต้นทาง** (แบบเดียวกับบั๊ก A-6519 ที่ fabricouts) → ตรวจซ้ำด้วย `withdrawId` แล้วพบว่า **`withdrawId` ของ `materialrequisitions` legacy ทุกแถวเป็นค่าคงที่ `"siriporn"`** (ไม่ใช่รหัสบิลที่ unique จริง เป็นแค่ placeholder ตอน sync จาก MySQL เดิม) — เมื่อตรวจแถวจริงทีละแถว (เช่น กลุ่ม "C 20/2 (PST)" 50 แถว) พบว่าทุกแถวมี `withdrawDate`, `spool`, `weightWithdrawn` **ต่างกันจริง** ไม่ใช่ข้อมูลซ้ำ → **ไม่ใช่บั๊กซ้ำแบบ A-6519** เป็น false positive จากการใช้ `withdrawId` เป็นตัวเช็ค (field นี้ใช้เก็บ placeholder ไม่ใช่ unique bill code สำหรับ legacy requisition data)

ตัวอย่างที่ชัดสุด: **CVC 45 COMB** ติดลบทั้งหมดมาจากแถว `req_orphan` เดียว (legacy record `materialId=NULL`, spool=1,224, weight=3,009.28 → avg 2.458 kg/spool) เทียบกับ avgTotal ของกลุ่ม (2.220 kg/spool) ต่างกันแค่ ~11% แต่เพราะกลุ่มนี้มี **แถว materials เดียว (1,284 spool)** จึงไม่มี volume ไปกลบผลต่างเล็กๆ นี้ได้เลย

**ทำไม avgUsed > avgTotal เล็กน้อย:** น้ำหนัก "รับเข้า" (`materials.weightKgSum`) กับ "เบิกออก" (`weightWithdrawn` ใน requisitions/outsides) ถูกบันทึกคนละจุดคนละวิธีใน Laravel เดิม (คนละครั้งที่ชั่ง คนละมาตรฐานปัดเศษ) — เป็น**ความคลาดเคลื่อนของข้อมูลต้นทางตามธรรมชาติ ไม่ใช่บั๊ก sync/matching** (ยืนยันแล้วว่า materialId ไม่รั่วข้ามกลุ่มสักแถวเดียวในทั้ง 8 กลุ่ม) ตรงกับที่เคยพบ shortfall ทำนองเดียวกันตอนทดลอง FIFO ในข้อ 9

**สรุปข้อ 13:** ทั้ง 8 กลุ่มไม่มีบั๊กโค้ด (ไม่มี mis-link ข้ามกลุ่ม, ไม่มีธุรกรรมซ้ำจริง) — เป็นผลรวมของ (ก) กลุ่มเหล่านี้เป็น yarnType ที่มี volume น้อยและเหลือของใกล้หมด + (ข) ความคลาดเคลื่อนตามธรรมชาติของน้ำหนักที่บันทึกตอนรับเข้า vs ตอนเบิกออกในข้อมูลต้นทาง Laravel เดิม พอกพูนสะสมจนติดลบเล็กน้อยที่ระดับกลุ่ม (ลบมากสุด -20,739 kg จากกลุ่มที่มี volume ใหญ่สุดในบรรดา 8 กลุ่ม คือ ~24% ของ totalWeightKg) — ไม่ต้องแก้โค้ด เป็นข้อจำกัดของข้อมูลต้นทางเช่นเดียวกับที่สรุปไว้ในข้อ 9-10
