## 3. หลักฐานเชิงโค้ด — ทำไมบั๊กเกิดจาก MySQL ไม่ใช่จาก sync

ตรวจโค้ด sync/migration ทั้ง 3 ตัวที่แตะตาราง `fabricouts`:

| Script | วิธี insert | conflict handling |
|---|---|---|
| `scripts/migrate-from-mysql.ts:205` | `prisma.fabricOut.upsert({ where: { id: f.id }, ... })` | upsert บน `id` |
| `scripts/sync-from-mysql.ts:357,379` | `id: Number(f_.id)` ตรงจาก MySQL, `createMany({ skipDuplicates: true })` | skip ถ้า id ซ้ำ |
| `scripts/sync-from-mysql-upsert.ts:428,452` | `INSERT ... ON CONFLICT ("id") DO UPDATE` | conflict บน `id` |

**ทุก code path ผูก Postgres `id` = MySQL `id` แบบ 1:1 เสมอ และทุกตัวป้องกัน id ซ้ำอยู่แล้ว** (skipDuplicates / upsert / ON CONFLICT) → เป็นไปไม่ได้ที่การรัน sync ซ้ำ (แม้รันหลายรอบ) จะสร้างแถวใหม่ที่มี id ต่างออกไปสำหรับ MySQL row เดิมแถวเดียวกัน

ดังนั้นการที่ Postgres มี 2 แถวจริงคนละ id ต่อเนื่องกันสนิทไม่มีช่องว่าง **แปลว่า MySQL ต้นทางต้องมี 390 แถวจริงอยู่แล้วก่อนถูก sync เข้ามา**

## 6. ตรวจอีก 29 บิลที่เหลือทีละเคส — ไม่พบ duplicate เพิ่มเติม

**วิธีตรวจรอบแรก (เทียบตำแหน่ง fold) ใช้ไม่ได้** — `fold` เป็นเลขลำดับที่เริ่มนับ 1 ใหม่ทุกครั้งที่มี `refId` ใหม่ (ตาม comment ใน schema: *"Sequential roll number within this delivery"*) ทำให้ทุกบิลดูเหมือน "ไม่ตรงกัน" ปลอมๆ เพราะเลข fold ชนกันโดยบังเอิญ (fold=1 มีทุกกลุ่มเสมอ)

**วิธีที่ถูกต้อง:** เทียบ **multiset ของค่า `sumYard`** ทั้งกลุ่ม (ไม่สนลำดับ) — วิธีนี้ยืนยัน 8 บิลข้างต้นได้แม่นเป๊ะ (match 100%) นำมาทดสอบกับ 29 บิลที่เหลือ:

**ไม่มีบิลไหน match แบบ exact เลยสักบิลเดียว** แบ่งผลได้ 3 กลุ่ม:

- **ไม่ทับซ้อนกันเลย (5 บิล):** `A-1183, A-1208, A-1322, A-5916, A-6528` — yard overlap = 0%, จำนวนม้วน/fabricStruct/receiveName ต่างกันชัดเจน → ข้อมูลจริงคนละรายการ
- **ทับซ้อนบางส่วนแบบบังเอิญ (16 บิล):** จำนวนม้วน/ยอดหลารวมของแต่ละกลุ่มต่างกันมาก (เช่น 12 พับ vs 65 พับ) overlap fraction ต่ำ-ปานกลาง (4%–41%) สอดคล้องกับค่า sumYard เป็นตัวเลขกลมๆ ที่พบซ้ำได้เองในอุตสาหกรรมผ้า (90, 100, 118, 122 หลา ฯลฯ) ไม่ใช่หลักฐาน duplication
- **ทับซ้อนสูง + fabric/ผู้รับตรงกัน + เวลาใกล้กัน แต่ตรวจละเอียดแล้วไม่ใช่ duplicate (8 บิล):** `A-1178, A-1179, A-1211, A-1248, A-1261, A-1316, A-6147, A-6292` — id ต่อเนื่องกัน สร้างห่างกันแค่ 1–90 นาที (คล้าย pattern ของ 8 บิลที่ยืนยันว่าเป็น duplicate) **แต่เนื้อหา (fold/yard) ไม่เหมือนกันจริง** ตัวอย่างที่ชัดสุด:
  - **A-1261**: 3 sessions (50, 50, 50 พับ — จำนวนเท่ากันเป๊ะ) แต่ **fabricStruct ไม่เหมือนกัน** ระหว่าง session แรกกับ session 2-3 (คนละเนื้อผ้า) → เป็นการส่งผ้าคนละล็อตใช้เลขบิลเดียวกัน ไม่ใช่ duplicate แน่นอน
  - **A-1248**: 3 sessions (205, 47, 320 พับ) ห่างกัน ~1 ชม.ในวันเดียวกัน ผู้รับ = "มารับเอง" → ลูกค้ามารับของหลายรอบในวันเดียว
  - **A-6147**: 20 vs 18 พับ ห่างกัน 1.5 นาที fabric/ผู้รับตรงกัน แต่ยอดม้วน/หลาไม่เท่ากัน overlap แค่ 50% → เข้าข่าย "แบ่งกรอกของจริงเป็น 2 รอบติดกันเพราะของเยอะ" มากกว่า duplicate
  - **A-6292**: 48 vs 44 พับ ห่างกัน ~2 ชม. 11 นาที → น่าจะเป็นส่งของ 2 รอบจริงในวันเดียวกัน

**สรุป:** ไม่มีบิลไหนใน 29 บิลที่เหลือมี "จำนวนพับเท่ากัน + ยอดหลารวมเท่ากัน + เนื้อหาตรงกันทั้งหมด" แบบ 8 บิลที่ยืนยันแล้ว — ทุกกรณีมีจำนวนพับ/ยอดหลา/หรือแม้แต่ fabricStruct ต่างกันจริง สอดคล้องกับสมมติฐานว่าเป็นการแบ่งกรอกของจริงเดียวกันเป็นหลายรอบ (session ใหม่ทุกครั้งที่กรอกฟอร์มใหม่ในระบบ Laravel เดิม) ไม่ใช่การกรอกซ้ำสิ่งเดียวกัน
