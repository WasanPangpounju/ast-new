# สืบสวน: ยอดคงคลัง (stock-summary) เพี้ยนหลังแก้ normalize หน้ากว้าง (commit d865535)

_สืบสวนเท่านั้น 2026-08-14 — อ่านข้อมูลอย่างเดียว 100% ไม่มีการ UPDATE/DELETE/INSERT ใดๆ ระหว่างการสืบสวน สคริปต์ investigate ที่สร้างขึ้นระหว่างทางถูกลบออกจาก repo หลังใช้งานเสร็จ_

**สถานะ: โค้ดหลัง fix ตรวจสอบแล้วว่าคำนวณถูกต้อง 100% เทียบกับข้อมูลจริงในฐานที่ตรวจสอบได้ — แต่ตัวเลข "ก่อนแก้" ที่ใช้เปรียบเทียบ reproduce ไม่ได้จากฐานข้อมูลเดียวกัน ต้องขอข้อมูลเพิ่มจากผู้รายงานก่อนสรุปว่าเป็นบั๊กจากโค้ด**

## สรุปสั้น (TL;DR)

- **โค้ดหลังแก้ (ปัจจุบัน) คำนวณถูกต้องและสอดคล้องภายในตัวเอง 100%** — reproduce ตัวเลข "ใหม่" ที่รายงานมาได้ตรงเป๊ะทั้งสองบรรทัด (155,841 / 0 สำหรับ C19.3/2 และ 0 / 126,227 สำหรับ C20/2) จากการรัน query จริงตรงๆ กับข้อมูลใน DB
- **"เบิกออก 0" ของ C19.3/2 ไม่ใช่บั๊ก** — ตาราง `fabricouts` ไม่มีแถวไหนเลยที่ `fabricStruct` ตรงกับ "C19.3/2 * C19.3 / 39 * 37" จริงๆ (มีแต่ "C20/2 * C19.3 / 39 * 37") เป็นแบบนี้อยู่แล้วในข้อมูลดิบ ไม่เกี่ยวกับ normalize หน้ากว้างเลย — struct ตอนนำเข้ากับตอนเบิกออกของ "yarn เดียวกัน" นี้ถูกบันทึกด้วยชื่อ struct คนละชื่อกันตั้งแต่ต้นทาง (data quality เดิม ไม่ใช่โค้ด)
- **1,880 หน่วยที่ต่างกันในยอดเบิกออกที่ผู้รายงานคำนวณเอง เกิดจากฐานเทียบไม่ครบ ไม่ใช่ข้อมูลหาย** — `fabricouts` สำหรับกลุ่ม C20/2 จริงๆ มี fabricW ย่อย **4 แบบ** คือ `50` (31,473), `50/V` (61,578), `50/V-PST` (1,512), `50/V1-V1` (31,664) รวม = 126,227 ตรงกับตัวเลข "ใหม่" เป๊ะ — แต่ผู้รายงานเทียบจากรายการ "เก่า" ที่มีแค่ 3 บรรทัด (ไม่มีแถว `50/V`=61,578) ทำให้ผลรวมที่คำนวณเองไม่ตรง
- **จุดที่ reproduce ไม่ได้: ตัวเลข "ก่อนแก้" (233,029 / 63,241 / 63,354 ฯลฯ)** — ลองรัน query แบบเดิม (ไม่ normalize fabricW, ไม่ trim, เหมือนโค้ดก่อน commit d865535 ทุกตัวอักษร) กับข้อมูลใน DB ชุดเดียวกันนี้ **ได้ผลไม่ตรงกับตัวเลขที่รายงานว่าเป็น "ก่อนแก้"** เลย (ได้ 155,841/0 สำหรับ C19.3/2, ไม่ใช่ 233,029/63,241) — แปลว่า "ก่อน" กับ "หลัง" ที่เอามาเทียบกัน **ไม่ได้มาจากข้อมูลชุดเดียวกัน** อย่างน้อยก็ไม่ใช่ข้อมูลใน local dev DB ที่ใช้สืบสวนนี้
- **ข้อสังเกตสำคัญ: local dev DB ที่ใช้สืบสวน (`ast_new` บน localhost) มีข้อมูลนิ่งมาตั้งแต่ปลายเดือนพฤษภาคม** — `createDate` ล่าสุดของทั้ง `stockfabrics` และ `fabricouts` คือ 2026-05-24 / 2026-05-28 (ไฟล์ `.env` เองก็แก้ล่าสุด 7 พ.ค.) ในขณะที่วันนี้คือ 14 ส.ค. — ห่างกันเกือบ 3 เดือนที่ไม่มี record ใหม่เข้าเลย บ่งชี้ว่านี่คือ DB สำหรับ dev/ทดสอบที่ไม่ sync กับข้อมูลที่ใช้ทดสอบจริงตอนเทียบ "ก่อน/หลัง" (น่าจะเป็น DB คนละชุด หรือ environment คนละตัวกับที่ทดสอบผ่านหน้าเว็บจริง)

**ข้อสรุป:** จากมุมมองโค้ด — `stock-summary/route.ts` และ `stock-movement/route.ts` หลังแก้ไม่มีบั๊กที่ทำให้ข้อมูลหายจริง (ดูหัวข้อ 3 เรื่อง SQL GROUP BY ป้องกัน collision ไว้แล้ว) แต่ไม่สามารถยืนยัน/ปฏิเสธข้อสังเกตของผู้รายงานได้ 100% เพราะ reproduce ตัวเลข "ก่อนแก้" ไม่ได้จากฐานข้อมูลที่ตรวจสอบได้ — ต้องยืนยันก่อนว่าตัวเลข "ก่อน" กับ "หลัง" มาจาก environment/DB เดียวกัน และ filter (vatType, asOfDate) เดียวกันหรือไม่

## 1. เทียบโค้ดก่อน/หลัง commit d865535

`stock-summary/route.ts` เปลี่ยน 2 อย่าง:
1. เพิ่ม `fabricWNorm` — ตัด fabricW เหลือเฉพาะตัวเลขนำหน้า (`50/V1-V1` → `50`) แล้วใช้ทั้งใน `SELECT` และ `GROUP BY` ของทั้ง `stockfabrics` (in) และ `fabricouts` (out)
2. ลบ `.filter(r => r.balanceYard !== 0)` ที่เคยตัดแถว balance=0 ออกจากตารางรายละเอียด (แต่การ์ดสรุปยอด `totalIn/totalOut` รวมทุกแถวอยู่แล้วไม่ว่าจะมี filter นี้หรือไม่ — เพราะ `totalIn`/`totalOut` คำนวณจาก `inRows`/`outRows` ตรงๆ ก่อนสร้าง `map` ด้วยซ้ำ)

`stock-movement/route.ts` เปลี่ยนแบบเดียวกัน (normalize fabricW) แต่ไม่มี filter balance=0 ให้ตัดอยู่แล้ว

`export-out/route.ts` เปลี่ยนคนละเรื่อง (แก้ MAX-collapse ต่อบิล) ไม่เกี่ยวกับ endpoint ที่ผู้รายงานอ้างถึง

## 2. Reproduce ตัวเลข "ใหม่" จากข้อมูลจริง — ตรง 100%

Query ตรงจาก `stockfabrics`/`fabricouts` กรองด้วย `fabricStruct ILIKE '%19.3%' OR fabricStruct ILIKE '%C20%'` ได้กลุ่มที่เกี่ยวข้อง:

**stockfabrics (นำเข้า):**
| fabricStruct | fabricPattern | fabricW | n | sumYard |
|---|---|---|---|---|
| `C19.3/2  * C19.3  / 39 * 37` | `1/1` | `50` | 406 | **155,841** |

**fabricouts (เบิกออก), แยกตาม fabricW ดิบก่อน normalize:**
| fabricStruct | fabricPattern | fabricW | n | sumYard |
|---|---|---|---|---|
| `C20/2  * C19.3  / 39 * 37` | `1/1` | `50` | 83 | 31,473 |
| `C20/2  * C19.3  / 39 * 37` | `1/1` | `50/V` | 160 | 61,578 |
| `C20/2  * C19.3  / 39 * 37` | `1/1` | `50/V-PST` | 4 | 1,512 |
| `C20/2  * C19.3  / 39 * 37` | `1/1` | `50/V1-V1` | 82 | 31,664 |
| **รวม** | | (normalize → `50`) | 329 | **126,227** |

ตรงกับตัวเลข "ใหม่" ที่รายงานมาทุกตัว (155,841 / 0 และ 0 / 126,227) — ยืนยันว่า SQL หลัง normalize รวมกลุ่มถูกต้อง ไม่มีข้อมูลตกหล่นหรือซ้ำ และไม่มีการปนกันข้าม `fabricStruct` (C19.3/2 กับ C20/2 ไม่เคยถูกรวมกลุ่มกัน เพราะ normalize ทำเฉพาะ `fabricW` เท่านั้น)

ตรวจเพิ่มเติม: ไม่มีแถวไหนใน 2 ตารางนี้ที่ `deleted_at IS NOT NULL` สำหรับกลุ่มนี้ (soft-delete ไม่ใช่สาเหตุ) และ `createDate` ของทุกแถวอยู่ในช่วง ม.ค.–พ.ค. 2026 (ไม่มีแถวใหม่ที่เพิ่งถูกเพิ่มระหว่างวันที่ทดสอบ)

## 3. ทำไมโค้ดถึงไม่มีบั๊ก data-loss จากมุมมอง SQL/JS

ทั้ง `stock-summary` และ `stock-movement` ใช้ pattern เดียวกัน:
```ts
for (const r of outRows) {
  const key = `${r.fabricStruct}||${r.fabricPattern}||${r.fabricW}`
  const ex = map.get(key)
  if (ex) ex.outYard = Number(r.sumYard ?? 0)   // ← เขียนทับ ไม่ใช่บวกเพิ่ม (+=)
  else map.set(key, { ... })
}
```
บรรทัดนี้ใช้ `=` (เขียนทับ) แทน `+=` (บวกสะสม) ซึ่ง**จะเป็นบั๊กได้ก็ต่อเมื่อ** `outRows` จาก SQL มี 2 แถวขึ้นไปที่ map เป็น key เดียวกันใน JS — แต่เพราะ `fabricWNorm` ถูกใส่เข้าไปใน `GROUP BY` ของ SQL เอง (ไม่ใช่แค่ใน `SELECT`) PostgreSQL จึงการันตีว่าแต่ละ combination ของ `(fabricStruct, fabricPattern, fabricWNorm)` จะมีแค่ 1 แถวต่อ query อยู่แล้ว — ไม่มีทางเกิด key ซ้ำจาก query เดียวได้ในสถานการณ์ปัจจุบัน จึงยืนยันว่าไม่ใช่สาเหตุของบั๊กที่รายงานมา

**ข้อสังเกตเชิง defensive coding (ไม่ใช่สาเหตุบั๊กที่รายงาน แต่ควรระวังไว้):** โค้ดใช้ `=` แทน `+=` ทำให้ pattern นี้เปราะบาง — ถ้าในอนาคตมีการแก้ query (เช่น เพิ่มคอลัมน์เข้า SELECT โดยลืมเพิ่มเข้า GROUP BY ด้วย) จะทำให้ข้อมูลเงียบๆ หายไปโดยไม่มี error ใดๆ เตือน ควรเปลี่ยนเป็น `+=` เพื่อความปลอดภัยในระยะยาว (ไม่ได้แก้ในสืบสวนนี้ตามคำขอ)

## 4. จุดที่ reproduce ตัวเลข "ก่อนแก้" ไม่ได้

รัน query แบบ**เดิมทุกตัวอักษร** (ไม่มี `fabricWNorm`, group by `fabricW` ดิบ, มี `.filter(balanceYard !== 0)`) กับข้อมูลชุดเดียวกันนี้ ได้ผลลัพธ์สำหรับกลุ่มนี้เป็น:

| fabricStruct | fabricW | inYard | outYard |
|---|---|---|---|
| `C19.3/2 * C19.3 / 39 * 37` | `50` | 155,841 | 0 |
| `C20/2 * C19.3 / 39 * 37` | `50` | 0 | 31,473 |
| `C20/2 * C19.3 / 39 * 37` | `50/V` | 0 | 61,578 |
| `C20/2 * C19.3 / 39 * 37` | `50/V1-V1` | 0 | 31,664 |
| `C20/2 * C19.3 / 39 * 37` | `50/V-PST` | 0 | 1,512 |

ตัวเลขนี้**ไม่ตรง**กับ "ก่อนแก้" ที่รายงานมา (233,029/63,241 สำหรับ C19.3/2, 63,354 สำหรับ 50/V1-V1) เลยสักบรรทัดเดียว ยกเว้น `50/V-PST` = 1,512 ที่ตรงพอดี — แสดงว่าตัวเลข "ก่อนแก้" ที่ใช้เปรียบเทียบมาจากข้อมูลคนละชุดกับที่มีอยู่ใน DB นี้ตอนนี้ ไม่ใช่แค่โค้ดคนละเวอร์ชัน

## 5. สาเหตุที่เป็นไปได้ของความไม่ตรงกัน (ต้องยืนยันกับผู้รายงาน)

1. **environment/DB คนละชุด** — local dev DB (`ast_new` บน `localhost:5432`) มีข้อมูลนิ่งตั้งแต่ปลาย พ.ค. 2026 (`.env` แก้ล่าสุด 7 พ.ค.) แต่การทดสอบ "ก่อน/หลัง" ที่รายงานมาน่าจะทำผ่านหน้าเว็บจริง (staging/production) ซึ่งข้อมูลต่างจากที่นี่
2. **filter ต่างกัน** — `vatType` หรือ `asOfDate` ที่เลือกไว้ตอนดูหน้าจอ "ก่อน" กับ "หลัง" อาจไม่เหมือนกัน (ค่า default ของ `asOfDate` คือวันที่วันนี้ตอนโหลดหน้า ซึ่งถ้าโหลดคนละวันจะกรองข้อมูลต่างช่วงกัน)
3. **ข้อมูลถูกแก้ไข/sync ระหว่างสองครั้งที่ทดสอบ** — ถ้า "ก่อน" กับ "หลัง" ทดสอบห่างกันหลายชั่วโมง/วัน และมีการนำเข้า-เบิกข้อมูลจริงหรือ resync เกิดขึ้นระหว่างนั้น ตัวเลขจะเปลี่ยนได้โดยไม่เกี่ยวกับโค้ด
